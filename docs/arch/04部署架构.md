# acore-ranking 部署架构设计

## 一、部署模式

### 1.1 单体容器部署

前后端构建为**单一 Docker 镜像**，由 Express 统一托管：

| 层级 | 处理方式 | 说明 |
|------|---------|------|
| **前端** | Vite 构建产物 → 静态文件 | 由 Express `express.static()` 托管 |
| **后端** | Express API → `/api/*` 路由 | 业务逻辑、数据库查询、缓存 |
| **SPA Fallback** | `/*` → `index.html` | 支持 React Router BrowserHistory |

**优势**：
- 腾讯云 SCF 只需部署**一个云函数**，一个容器实例
- 减少网络延迟（前端→后端为同容器内部调用）
- 简化运维（单镜像、单容器、单日志流）
- 避免前后端分离部署的 CORS 和跨域配置复杂度

## 三、统一 Dockerfile

```dockerfile
# docker/Dockerfile
# 前后端统一构建，输出单一可运行镜像

# ============================================================
# Stage 1: 前端构建
# ============================================================
FROM node:20-alpine AS frontend-builder
WORKDIR /app/frontend

COPY frontend/package*.json ./
RUN npm ci

COPY frontend/ ./
RUN npm run build
# 输出: /app/frontend/dist/ (HTML/CSS/JS/静态资源)

# ============================================================
# Stage 2: 后端构建
# ============================================================
FROM node:20-alpine AS backend-builder
WORKDIR /app/backend

COPY backend/package*.json ./
RUN npm ci

COPY backend/ ./
RUN npm run build
# 输出: /app/backend/dist/ (JS + .d.ts)

# ============================================================
# Stage 3: 生产运行镜像
# ============================================================
FROM node:20-alpine AS production
WORKDIR /app

# 安装生产依赖（仅 backend 的 dependencies）
COPY backend/package*.json ./
RUN npm ci --only=production && npm cache clean --force

# 复制后端构建产物
COPY --from=backend-builder /app/backend/dist ./dist

# 复制前端构建产物到后端静态文件目录
COPY --from=frontend-builder /app/frontend/dist ./dist/public

# 非 root 用户运行（安全最佳实践）
RUN addgroup -g 1001 -S nodejs && \
    adduser -S nodejs -u 1001
USER nodejs

# 腾讯云 SCF Web 容器默认端口
EXPOSE 9000

CMD ["node", "dist/server.js"]
```

### 镜像体积优化

| 阶段 | 体积 | 说明 |
|------|------|------|
| 前端构建 | ~300MB（含 node_modules）| 中间层，不进入最终镜像 |
| 后端构建 | ~400MB（含 node_modules）| 中间层，不进入最终镜像 |
| **生产镜像** | **~120MB** | 仅含运行时 + 编译产物 + 生产依赖 |

## 四、Express 静态文件托管配置

生产环境下，Express 同时承担 API 服务和静态文件托管职责：

```typescript
// backend/src/app.ts

import express, { Application } from 'express';
import path from 'path';

export function createApp(): Application {
  const app = express();

  // 1. 安全中间件
  app.use(helmet({ frameguard: false }));
  app.use(iframeCors);

  // 2. 解析中间件
  app.use(express.json());
  app.use(express.urlencoded({ extended: true }));

  // 3. 日志与格式化
  app.use(requestLogger);
  app.use(responseFormatter);

  // 4. 鉴权
  app.use(apiKeyAuth);

  // 5. API 路由（必须在静态文件之前注册，避免被 SPA fallback 拦截）
  app.use('/api/online', onlineRoutes);
  app.use('/api/ranking', rankingRoutes);
  app.use('/api/hardcore', hardcoreRoutes);
  app.use('/api/achievement', achievementRoutes);
  app.use('/api/banlist', banlistRoutes);
  app.use('/api/character', characterRoutes);
  app.use('/api/health', healthRoutes);

  // 6. 静态文件托管（前端构建产物）
  app.use(express.static(path.join(__dirname, 'public')));

  // 7. SPA fallback：所有非 API 请求返回 index.html
  // 支持 React Router 的 BrowserHistory 模式
  app.get('*', (_req, res) => {
    res.sendFile(path.join(__dirname, 'public', 'index.html'));
  });

  // 8. 全局错误处理（末尾注册）
  app.use(errorHandler);

  return app;
}
```

### 路由优先级说明

```
请求到达顺序：
  /api/online/count    → API 路由处理（第 5 步）
  /assets/icons/xxx.png → 静态文件（第 6 步）
  /ranking             → SPA fallback → index.html（第 7 步）
  /character/xxx       → SPA fallback → index.html（第 7 步）
```

> **注意**：API 路由必须注册在 `express.static()` 之前，否则 `/api/health` 等路径可能被误判为静态文件请求。

## 六、腾讯云 SCF 部署

### 6.1 部署流程

```
代码提交 → GitHub Actions 触发
    │
    ▼
┌─────────────────────┐
│ 1. 构建前端 (Vite)   │
│ 2. 构建后端 (tsc)    │
│ 3. Docker 构建       │
│ 4. 推送 TCR 镜像仓库  │
└─────────────────────┘
    │
    ▼
┌─────────────────────┐
│ 5. 触发 SCF 部署     │
│    更新容器镜像版本   │
│ (UpdateFunctionCode)│
└─────────────────────┘
    │
    ▼
腾讯云 SCF Web 容器运行（监听 9000）
```

### 6.2 TCR 镜像仓库配置

| 配置项 | 值 | 说明 |
|--------|-----|------|
| 仓库地址 | `ccr.ccs.tencentyun.com` | 腾讯云容器镜像服务（个人版） |
| 命名空间 | `${TCR_NAMESPACE}`（`lokta`） | 项目级命名空间 |
| 镜像名称 | `acore-ranking` | 与项目名称一致 |
| 镜像标签 | `latest` / `${BRANCH}-${SHORT_SHA}` | `latest` 为滚动标签；分支标签按提交唯一，回滚用后者 |

### 6.3 SCF 函数配置

| 配置项 | 值 | 说明 |
|--------|-----|------|
| 地域 | `ap-beijing` | 密钥需有该地域权限 |
| 函数名 | `acore-ranking` | 单函数（前后端同镜像） |
| 命名空间 | `staging`（测试）/ `production`（生产） | `develop` 分支流水线只更新 `staging` |
| 运行时 / 部署模式 | `CustomImage` / `image` | 镜像部署，按 `ImageConfig.ImageUri` 拉取 TCR 镜像 |
| 镜像端口 | `9000` | 与 `docker/Dockerfile` 的 `EXPOSE 9000` 一致 |
| 环境变量 | 控制台配置 | `DB_URL` / `REDIS_URL` / `SERVER_NAME` 等由人工在控制台维护，**流水线不覆盖** |

**部署机制**：`UpdateFunctionCode`，只传 `Code.ImageConfig`（`ImageType` / `ImageUri` / `ImagePort`），
其余字段一律不传——函数的环境变量、端口、超时、网络配置都是人工在控制台调过的，
若用 Serverless Framework 全量 `deploy` 会把这些值打回模板默认值。

镜像地址带摘要（`{registry}/{namespace}/{image}:{tag}@sha256:{digest}`）：SCF 按摘要拉取，
不依赖标签解析，避免推送后立刻部署时因仓库同步延迟拉到旧镜像。

### 6.4 流水线所需的 GitHub Secrets

| Secret | 用途 |
|--------|------|
| `TCR_USERNAME` / `TCR_PASSWORD` | 登录 TCR 推送镜像 |
| `TCR_NAMESPACE` | TCR 命名空间（`lokta`） |
| `TENCENT_SECRET_ID` / `TENCENT_SECRET_KEY` | 调用 SCF API 更新函数镜像 |

可选仓库变量（未设置时取默认值）：`SCF_REGION`（`ap-beijing`）、`SCF_NAMESPACE`（`staging`）、
`SCF_FUNCTION_NAME`（`acore-ranking`）。

## 七、CI/CD 流水线

### 7.1 GitHub Actions 工作流

工作流文件：`.github/workflows/ci.yml`。四个 job 串成一条流水线：

| Job | 触发 | runner | 产物 / 动作 |
|-----|------|--------|-------------|
| `frontend` | push / PR | `ubuntu-latest` | 前端 lint + 单测 + Vite 构建 |
| `backend` | push / PR | `ubuntu-latest` | 后端 lint + `tsc --noEmit` + Dockerfile 静态检查 + 单测 + 构建 |
| `docker` | push 到 `develop` / `main` | `self-hosted`（Mac mini，持久 buildx builder） | 构建镜像并推送 TCR（`:latest` + `:${BRANCH}-${SHORT_SHA}`），输出带摘要的 `image_uri` |
| `deploy-scf` | push 到 `develop` | `self-hosted` | 把 `image_uri` 更新到 SCF `staging` 命名空间的 `acore-ranking` 函数 |

PR 只跑检查与构建；只有合入 `develop` / `main` 才产出镜像；`deploy-scf` 目前只对 `develop` 生效
（`main` → `production` 命名空间待启用，把 `if` 条件与 `SCF_NAMESPACE` 拆开即可）。

```yaml
  deploy-scf:
    name: Deploy to SCF / 部署腾讯云函数
    runs-on: [self-hosted]
    needs: [docker]
    if: github.event_name == 'push' && github.ref == 'refs/heads/develop'
    timeout-minutes: 15
    env:
      SCF_REGION: ${{ vars.SCF_REGION || 'ap-beijing' }}
      SCF_NAMESPACE: ${{ vars.SCF_NAMESPACE || 'staging' }}
      SCF_FUNCTION_NAME: ${{ vars.SCF_FUNCTION_NAME || 'acore-ranking' }}
      SCF_IMAGE_URI: ${{ needs.docker.outputs.image_uri }}
      TENCENT_SECRET_ID: ${{ secrets.TENCENT_SECRET_ID }}
      TENCENT_SECRET_KEY: ${{ secrets.TENCENT_SECRET_KEY }}

    steps:
      - uses: actions/checkout@v4.2.2
      - uses: actions/setup-node@v4.3.0
        with:
          node-version: '20'
          cache: 'npm'
          cache-dependency-path: scripts/deploy/package-lock.json
      - working-directory: scripts/deploy
        run: npm ci
      - working-directory: scripts/deploy
        run: npm run deploy:scf
```

### 7.1.1 部署脚本

`scripts/deploy/scf-update-image.mjs`（依赖 `tencentcloud-sdk-nodejs-scf`，独立 package.json，不进镜像）：

1. 校验必填环境变量与镜像地址格式（必须带 `@sha256:` 摘要）；
2. 调 `UpdateFunctionCode` 只换 `Code.ImageConfig.ImageUri`；
3. 轮询 `GetFunction`，直到状态 `Active` 且镜像摘要一致（`UpdateFailed` 或 5 分钟超时即失败退出）。

本地手工部署同一函数（与流水线等价，用于回滚或应急）：

```bash
cd scripts/deploy && npm ci
TENCENT_SECRET_ID=... TENCENT_SECRET_KEY=... \
SCF_NAMESPACE=staging SCF_FUNCTION_NAME=acore-ranking SCF_REGION=ap-beijing \
SCF_IMAGE_URI="ccr.ccs.tencentyun.com/lokta/acore-ranking:<tag>@sha256:<digest>" \
  npm run deploy:scf
```

## 十、前端构建产物路径说明

### Vite 配置调整

前端构建输出目录使用默认 `frontend/dist`，在 Dockerfile Stage 3 中被复制到后端产物目录：

```typescript
// frontend/vite.config.ts

export default defineConfig({
  // ... 其他配置
  build: {
    outDir: 'dist',           // 默认输出目录
    emptyOutDir: true,        // 构建前清空
    // 前端产物最终被复制到 backend/dist/public/
  },
});
```

### 生产环境 API 调用

由于前后端同域部署，前端 API 调用无需指定完整域名：

```typescript
// src/shared/api/client.ts

const API_BASE_URL = import.meta.env.VITE_API_BASE_URL || '';
// 生产环境: VITE_API_BASE_URL = ''（空字符串）
// 请求 /api/online/count 会被同域 Express 处理
```

开发环境可通过 `.env.development` 配置代理：

```bash
# frontend/.env.development
VITE_API_BASE_URL=http://localhost:9000
```
